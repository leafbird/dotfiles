# 워크노트 워크플로우 개선 제안서

> 대상: `agents-worknotes.md`의 다음 개정 검토
>
> 작성일: 2026-08-24
>
> 목적: 이미 쌓인 작업 근거와 인수인계 품질은 보존하면서, 재개 시점에 현재 상태를 더 빠르고 확실하게 복구한다.

## 범위와 전제

- 워크노트는 프로젝트의 영구 저장소이며, 코드·스크립트·외부 시스템의 정본을 대체하지 않는다.
- 이 제안은 기존 프로젝트 전체를 소급 정리하거나 폴더 구조를 일괄 이주하는 작업이 아니다. **새로 만들거나 다시 여는 프로젝트부터** 적용한다.
- `TODO.md`는 정의된 필수 구성요소가 아니다. 프로젝트 성격에 따라 사용해도 되고, 구현 체크리스트나 README의 다음 행동으로 대체해도 된다.
- 대량 변환 코퍼스처럼 일반적인 프로젝트 작업 흐름과 다른 저장소는 이 제안의 대상이 아니다.
- 핸드오프는 기존처럼 사용자의 명시 요청이 있을 때만 작성한다.

## 관찰

현재 방식은 조사·결정·검증·인수인계를 날짜 문서로 남기는 데 강하다. 특히 긴 작업은 근거와 "다시 밟지 말 것"이 잘 보존된다.

다만 다음 세션에서 재개할 때는 README, 최신 handoff, 구현 문서, TODO 중 어디가 현재 상태의 최종본인지 사람이 판단해야 할 때가 있다. 문서가 부족해서가 아니라, **현재성의 단일 진입점과 갱신 규칙이 느슨해서** 생기는 비용이다.

## 제안 1 — 재개 대상 프로젝트에만 `재개 진입점`을 둔다

### 적용 대상

아래 중 하나에 해당하면 재개 대상 프로젝트다.

- 다음 세션이나 다른 에이전트가 이어서 작업할 가능성이 있다.
- 외부 의존성, 장기 조사, 진행 중 구현처럼 현재 상태가 계속 변한다.
- 사용자가 핸드오프를 요청했다.

단발성 조사·완료 직후 아카이브할 작업에는 적용하지 않는다.

### 최소 계약

재개 대상 프로젝트의 `README.md` 상단에 다음 네 항목만 유지한다.

```md
## 재개 진입점

- 상태: 진행 중 | 대기 | 보류 | 완료
- 마지막 의미 있는 갱신: YYYY-MM-DD — 한 줄 요약
- 다음 행동: 가장 가까운 행동 1개와 그 정본 문서 링크
- 먼저 읽을 문서: 현재 상태를 판정할 문서 1~3개
```

여기서 README는 상세 이력의 사본이 아니다. "어디서 이어야 하는가"만 답한다. 상세한 사실·근거·실험 결과는 기존 날짜 문서, 구현 문서, 리서치 문서에 그대로 둔다.

`TODO.md`가 이미 유용한 프로젝트라면 `다음 행동`은 TODO 항목으로 연결한다. TODO가 없다면 구현 체크리스트 또는 README의 한 줄 행동을 정본으로 삼는다.

### 기대 효과

- 새 세션의 첫 읽기 순서가 프로젝트마다 예측 가능해진다.
- README가 최신 상세 기록을 중복하지 않아 유지 비용이 작다.
- 기존 프로젝트별 특성(봇 운영 문서, 구현 체크리스트, 조사 노트)을 존중한다.

## 제안 2 — 상태 변경 때 `한 곳만` 되돌려 갱신한다

### 규칙

조사 결과가 결정을 바꾸거나, 구현 단계가 완료·보류·대기로 바뀌는 등 **다음 행동이 달라지는 상태 변경**이 생기면 다음을 수행한다.

1. 근거와 상세 결과는 적합한 날짜 문서·구현 문서·리서치 문서에 기록한다.
2. 재개 진입점의 `상태`, `마지막 의미 있는 갱신`, `다음 행동`만 갱신한다.
3. 핸드오프를 작성했다면, 그 문서에도 다음 행동을 적되 README의 진입점과 모순되지 않게 한다.

모든 작은 편집마다 README를 갱신할 필요는 없다. 다음 세션의 시작점이 바뀌었을 때만 갱신한다.

### 완료와 보류

- 완료: README에 결과와 정본 링크를 남긴 뒤 `_archived/` 이동 여부를 판단한다.
- 보류: 이유·재개 조건·다음 확인 시점을 `다음 행동` 또는 연결 문서에 명시한다.
- 외부 회신 대기: "누가 / 무엇을 / 언제까지"를 적는다. 날짜가 지나면 상태를 다시 판정한다.

### 기대 효과

- "무엇이 최신인가"를 문서 수정 시각에 의존하지 않는다.
- 핸드오프는 세션용 상세 기록으로, README는 프로젝트 재개용 안내로 역할이 분리된다.
- 진행 기록을 줄이지 않고도 재개 비용을 낮춘다.

## 적용 방법

1. 다음에 다시 여는 장기 프로젝트 하나에서만 시범 적용한다.
2. README 상단에 `재개 진입점`을 추가하고, 기존 정본 문서로 링크한다.
3. 다음 세션에서 그 프로젝트를 재개할 때 "README만 읽고 다음 행동과 필요한 문서를 3분 안에 판정할 수 있었는가"를 확인한다.
4. 만족하면 `agents-worknotes.md`에 짧은 규칙으로 편입한다. 불편하면 항목 수나 적용 대상을 줄인다.

## `agents-worknotes.md`에 넣을 후보 문구

```md
### 재개 대상 프로젝트의 진입점

다음 세션·다른 에이전트가 이어서 작업할 가능성이 있는 프로젝트는 README 상단에
`재개 진입점`을 둔다. 여기에는 상태, 마지막 의미 있는 갱신, 다음 행동, 먼저 읽을
정본 문서만 적는다. 상세 기록을 중복하지 않는다.

다음 행동이 바뀌는 의미 있는 상태 변경이 있으면, 근거 문서를 기록한 뒤 재개 진입점도
갱신한다. `TODO.md`는 선택 사항이며, 프로젝트가 사용하는 다른 체크리스트가 정본일 수 있다.
```

- "상태" 값에 `대기`와 `보류`를 구분할지

## 타당한 부분

- 진단이 맞다. 현행 1.3은 README를 "인덱스(프로젝트 개요, **현재 상태**, 파일 목록)"로 이미 정의해 두었으나,
  형식도 갱신 시점도 규정하지 않아 실제로 느슨하다. "문서가 부족한 게 아니라 현재성의 단일 진입점이 없다"는 관찰은 정확하다.
- 소급 적용 제외 + 시범 1개 후 편입이라는 규모 설정이 적절하다. 워크노트가 이미 수십 개 프로젝트라 일괄 이주는 실패했을 것이다.
- 실제 편입 문구가 10줄뿐이다. 규칙은 짧아야 지켜진다.
- `TODO.md`를 선택사항으로 못박은 것. 현행 문서에서 `TODO.md`는 예시로만 등장하고 정의가 없어, 이 정리는 모호함을 없앤다.

## 보완이 필요한 지점

### 1. stale 진입점 대책 부재 — 가장 큰 구멍

없는 README보다 **틀린 README가 더 나쁘다.** 진입점을 믿고 읽었는데 2주 전 상태면 재개 비용이 오히려 커진다.
제안 2가 "갱신하자"고 말하지만 지침일 뿐이고, 어겼을 때 감지할 방법이 없다. 판정 규칙 한 줄이 필요하다.

```md
`마지막 의미 있는 갱신` 날짜가 그 프로젝트의 최신 날짜 문서보다 오래되면 진입점을 신뢰하지 않는다.
최신 날짜 문서부터 읽어 상태를 재판정한 뒤 진입점을 고친다.
```

이러면 규율이 깨져도 자가복구된다. 추가로 **`handoff` 스킬에 README 진입점 동시 갱신을 넣을 것**을 권한다.
핸드오프를 쓰는 시점이 정확히 "다음 행동이 바뀐 시점"이므로, 사람 규율에 기대지 않는 갱신 트리거를 하나 확보할 수 있다.

### 2. "재개 대상" 필터가 필터 역할을 못 한다

기준 3개 중 첫 번째 "다음 세션이나 다른 에이전트가 이어서 작업할 **가능성**이 있다"는 사실상 모든 프로젝트에 해당한다.
결국 전체 적용이 되어 "소급 정리 아님"이라는 전제와 충돌한다. 관찰 가능한 기준으로 바꿔야 한다.

- 제안: **`handoffs/`에 파일이 1개 이상 있거나 `구현/` 진행 문서가 미완인 프로젝트**

### 3. 3장(구현 진행 문서)과의 갱신 빈도 경계가 흐리다

"작은 편집마다는 아니다"라고 했으나 "다음 세션 시작점이 바뀌었을 때"는 주관적이라,
에이전트가 체크박스 하나 채울 때마다 README를 건드릴 수 있다. 사건 기반으로 못박는 편이 낫다.

- 갱신 시점을 4개로 한정: **청크 완료 / 핸드오프 작성 / 완료·보류·대기 전환 / 외부 회신 대기 진입**

### 4. (부수) 편입 시 현행 문서도 함께 수정해야 한다

- `1.3`의 README 정의 줄 — 진입점을 그 하위 항목으로 편입해야 중복 정의가 생기지 않는다.
- `2.4` 읽기 트리거 — 이미 "README + 최신 핸드오프 + 주요 문서 순"을 규정하고 있어 진입점의 `먼저 읽을 문서`와 겹친다.

### 5장의 핵심

- **불변식**: `todo.md` 에 `- [x]` 가 있으면 규칙 위반. `grep` 으로 검증 가능한 조건이라 stale 되지 않는다.
- **"바로바로"의 실행 형태**: 닫히는 즉시 `todo.md` 에서 제거하되, 옮겨 담는 곳은 **그날의 단일 파일**에 append.
  항목마다 새 파일을 만들면 파일이 폭발하고, `reloadable` 도 실제로는 날짜 단위로 묶었다.
- **닫힘 3종**: 완료 ✅ · 기각 ⛔ · 넘김 ➡️ 모두 대상. 완료만 빼면 기각 항목이 영원히 남는다.
- **번호 영구 고정**: 닫힌 번호 재사용 금지. 타 문서·메모리가 `TODO-11` 식으로 참조 중이라 재사용하면 조용히 오독된다.
- **`구현/` 과의 경계**: 진행 문서의 `- [x]` 는 **지우지 않는다.** 즉시 퍼내기는 `todo.md` 전용.
- **진행 중 항목 금지**: 정본은 `p4 opened` / `구현/` / `handoffs/`. `reloadable` 이 2026-08-13 에
  「지금 손에 있는 것」 절을 폐지하고 634줄 → 261줄로 줄인 선례를 전 프로젝트 방침으로 채택.
