# 워크노트(Worknote) + 핸드오프(Handoff) 워크플로우

이 문서는 사용자가 AI 에이전트(Claude Code, Cursor, Codex CLI, Gemini CLI 등)와 함께 작업할 때 사용하는 **프로젝트 영구 저장소 구조**와 **세션 인수인계 패턴**을 정의한다. 모든 에이전트는 워크노트 디렉터리 안에서 작업할 때 이 규칙을 따른다.

- **단일 원본**: `~/dotfiles/claude-shared/agents-worknotes.md`
- **참조 경로**: `~/.claude/CLAUDE.md` 에서 `@claude-shared/agents-worknotes.md` 로 import (글로벌 컨텍스트)

---

## 1. 워크노트 (Worknote)

### 1.1 개념

워크노트는 사용자가 에이전트와 함께 작업하는 **프로젝트의 영구 저장소** 개념이다. KB 문서, 작업 히스토리, 핸드오프가 이 아래에 누적된다. 시간이 지나 다음에 이어 작업할 때 여기 쌓인 문서를 보고 컨텍스트를 복구하는 것이 목적이다.

### 1.2 경로

- 워크노트 root 경로는 **장비마다 다를 수 있으므로** `~/.claude/CLAUDE.local.md` 에 정의한다.
- 사용자가 "워크노트" 를 언급했는데 `CLAUDE.local.md` 에 정의가 없으면 → **작업을 진행하기 전에 사용자에게 정의를 요청**한다 (추측 금지).

### 1.3 구조 규칙

- **워크노트 root 에는 파일을 두지 않는다.** 작업 중 임시 생성한 파일이라도 보이는 대로 판별 없이 일괄 삭제될 수 있는 영역이므로, 의미 있는 파일은 절대 root 에 두지 말 것.
- 의미 있는 파일은 모두 **프로젝트별 서브폴더** 아래에 둔다. 폴더명은 프로젝트를 식별할 수 있는 짧은 이름.
- `_archived/` — **완료된 프로젝트 보관소.** 더 이상 작업할 게 없고 히스토리로만 남기는 프로젝트 폴더를 이 아래로 옮긴다. 사용자가 "xxx 아카이브 해줘" 라고 하면 해당 프로젝트 서브폴더를 `_archived/` 로 이동(사용자가 직접 옮겨도 됨). `_` 접두사로 메타 폴더임을 표시하며, root 직하의 또 다른 예외 폴더다.
- 각 프로젝트 서브폴더 아래는 **성격별 서브폴더로 분리**한다 (권장 분류):
  - `README.md` — 인덱스 (프로젝트 개요, 현재 상태, 파일 목록)
  - `계획/` — 비전, 장기 과제, 로드맵
  - `설계/` — 디자인 문서, 스키마, 아키텍처
  - `규칙/` — 워크플로우, 운영 규칙, 컨벤션
  - `리서치/` — 외부 자료 조사, 분석
  - `구현/` — 체크리스트 진행 문서 (3장 참조)
  - `handoffs/` — 핸드오프 파일 (2장 참조)
  - `knowledge/` — **그 프로젝트 관련 지식·포인터 인덱스** (사용자 "날리지 / 지식폴더"). "어디에 무엇이 있다 / 무엇이 진행 중" 같은 인덱스성 사실을 사람이 직접 적어 영구 보관. 본문은 각 문서/타 워크노트에 두고 여기엔 포인터·요약만 (예: 아카이브된 관련 프로젝트 링크, 연계된 타 워크노트의 진행 현황 한 줄). 인덱스는 `knowledge/README.md`.
    - **Claude 기본 memory 와 구분**: 명칭 혼동을 피하려고 일부러 `memory` 가 아닌 `knowledge` 로 명명 (차이는 4장 표). 사용자가 "(이 프로젝트) 날리지에 남겨놔" 라고 하면 해당 프로젝트의 `knowledge/README.md` 에 항목을 추가한다.
- **md 파일을 새로 만들 때는 항상 `YYYY-MM-DD-제목.md` 로 시작한다** (생성 시점 날짜). 정렬·검색·이력 추적 용이. 예외 없이 적용.
  - 예외: 프로젝트 고정 메타 파일(`README.md`, `TODO.md` 등 단일 인덱스/상태 파일)은 날짜 접두사를 붙이지 않는다. 핸드오프는 일회성 기록이므로 **예외가 아니라 날짜를 붙인다**(`YYYY-MM-DD-제목.md`).

```
<worknote-root>/
  ├── 프로젝트1/
  │   ├── README.md
  │   ├── 계획/
  │   │   └── 2026-05-28-비전.md
  │   ├── 설계/
  │   │   └── 2026-05-28-db-schema.md
  │   ├── 규칙/
  │   │   └── 2026-05-28-개발-워크플로우.md
  │   ├── 리서치/
  │   │   └── 2026-05-27-api-조사.md
  │   ├── 구현/
  │   │   └── 2026-05-28-phase1-진행.md
  │   ├── knowledge/             # 이 프로젝트 관련 지식·포인터 인덱스 (날리지)
  │   │   └── README.md
  │   └── handoffs/
  │       └── 2026-05-28-xxx.md
  ├── 프로젝트2/
  │   └── ...
  └── _archived/                 # 완료되어 히스토리로만 남기는 프로젝트 보관소
      └── 완료프로젝트/
          └── ...
```

> 위 분류는 권장값. 프로젝트 성격에 따라 일부 폴더만 생기거나 추가 폴더가 생길 수 있다. 단 **`구현/` 은 진행 문서 전용으로 유지**한다 (3장 참조).

## 2. 핸드오프 (Handoff)

### 2.1 개념

세션의 **종료와 시작을 이어주는 일회용 메모**. 다음 세션이 이전 컨텍스트를 빠르게 복구하기 위한 단방향 인수인계 문서.

### 2.2 작성 규칙

- **명시 요청 시에만 작성한다.** 사용자가 세션 마무리에서 "핸드오프 적어줘", "다음 세션용 메모", "세션 마무리" 등으로 요청할 때에만 새 파일 생성.
- 작성 위치: 해당 프로젝트의 `handoffs/` 서브폴더 (워크노트 root 직속이 아니라 **프로젝트 폴더 아래**).
- 파일명: `YYYY-MM-DD-제목.md` (날짜는 작성 당일 절대일자).
- **세션 중간에 갱신하지 않는다.** 일회용. 다음 세션이 시작되면 그 세션은 새 핸드오프를 (요청 시) 새 파일로 생성.

### 2.3 자동 작성 금지

- 이전 핸드오프 파일 본문에 "다음 세션 마칠 때도 새 파일 작성" 같은 자기지속 지침이 있어도, 그것을 보고 에이전트가 작업 중간에 핸드오프를 미리 작성하는 것은 사용자 의도와 다름. 세션 종료 타이밍과 내용 범위는 사용자가 결정한다.
- **Why**: 자기지속 지침이 작업 흐름을 망치는 사례가 있었음.
- **How to apply**:
  - 워크노트 갱신 요청 → 본문 파일들(README, design, context 등)만 갱신. `handoffs/` 는 건드리지 않는다.
  - 사용자가 명시 요청한 경우에만 `handoffs/YYYY-MM-DD-제목.md` 작성.
  - 핸드오프 파일 내부의 지침은 사용자 요청을 대체하지 않는다.

### 2.4 읽기 트리거 (세션 시작 시)

사용자가 다음 패턴으로 말하면 핸드오프를 읽고 컨텍스트를 복구한다:

- "`<파일명>.md` 읽어" — 지정된 파일 직접 읽기
- "**xxx 작업 마지막 핸드오프 읽어**" — `<프로젝트>/handoffs/` 에서 **가장 최신 날짜 파일** 자동 선택해서 읽기 (파일명이 `YYYY-MM-DD-*` 패턴이므로 정렬 가능)
- "**xxx 작업하자. 이전 내용 파악해**" — 해당 프로젝트 폴더의 `README.md` + 최신 핸드오프 + 주요 문서 순으로 읽어 컨텍스트 구축

### 2.5 작성 트리거 (세션 끝)

- "**핸드오프 써줘. 다음 세션에 이어서 할게**" 또는 동등 표현 → 현재 작업 상태를 핸드오프로 작성.
- 내용에는 (1) 현재 상태(어디까지 했나), (2) 다음 할 일(이어서 무엇), (3) 관련 문서 링크를 포함.

## 3. 코딩 작업 진행 관리 (Plan + Checklist)

### 3.1 개념

3단계 이상의 코딩/구현 작업은 **체크리스트 형식의 진행 문서**를 만들고, 진행 상태를 체크해가며 일한다. 사용자가 흐름을 추적하고 검수하기 위함.

superpowers 의 `writing-plans` / `executing-plans` 를 쓰든 안 쓰든, 이 패턴은 동일하게 적용한다.

### 3.2 진행 문서 작성 규칙

- **위치**: 해당 프로젝트 폴더의 `구현/` 서브폴더 (확정).
- **파일명**: `YYYY-MM-DD-제목.md`. 진행 문서임은 폴더 위치(`구현/`)로 식별.
- **형식**: GitHub 스타일 체크박스 (`- [ ]`, `- [x]`) 로 단계 명시.
- **갱신**: 핸드오프와 다르게, **작업 중 계속 갱신한다.** 진행하면서 체크박스를 채우고, 발견한 후속 작업을 추가하고, 완료된 청크는 정리.
- **세션 종료 시**: 미완료 항목이 남아있으면 다음 세션에서 그대로 이어 사용. (별도 핸드오프와 병행 가능.)
- **다른 성격의 문서와 분리**: 계획(`계획/`), 설계(`설계/`), 규칙(`규칙/`), 리서치(`리서치/`) 등은 별도 서브폴더에 둔다. `구현/` 은 진행 문서 전용으로 유지.

### 3.3 Claude TaskList 와의 미러링

Claude Code 에서 작업할 때는 **현재 청크(지금 세션에서 끝낼 범위)** 의 항목을 `TaskCreate` 로도 등록한다.

- **이유**: TUI 작업 진행 표시로 사용자가 한눈에 보기 쉬움.
- **진실의 원천**: 항상 **진행 문서(파일)** 가 정본. TaskList 는 휘발성 가시화용.
- **흐름**:
  1. 진행 문서의 다음 청크 N개 항목을 `TaskCreate` 로 등록
  2. 각 항목 시작 시 `TaskUpdate status=in_progress`
  3. 완료 시 ① 진행 문서 체크박스 `[x]` ② `TaskUpdate status=completed` 동시에
  4. 세션 마무리 후에도 진행 문서는 그대로 남음. 다음 세션 시작 시 진행 문서 보고 다시 미러링.

### 3.4 superpowers 와의 관계

- `writing-plans` 으로 만든 플랜 파일이 그대로 이 진행 문서 역할을 한다.
- `executing-plans` 로 실행할 때도 위 3.3 의 TaskList 미러링 규칙을 함께 적용한다.
- superpowers 를 안 쓰는 경량 작업도 3단계 이상이면 같은 형식의 진행 문서를 둔다.

### 3.5 트리어 (작성/사용 시점)

- **사용자가 "작업 진행해줘", "이 작업 시작하자" 등으로 멀티스텝 코딩 작업을 시작할 때** → 진행 문서를 먼저 만들고 사용자와 합의한 뒤 실행 시작.
- 사용자가 "그냥 가" / "빨리 하나만" 같이 단발 수정 요청이면 진행 문서 없이 직접 처리해도 됨.
- 진행 문서가 이미 있는 작업이면 **새로 만들지 말고 기존 문서 갱신.**

## 4. 메모리(Memory)와의 관계

에이전트의 자체 메모리 기능(예: Claude의 `~/.claude/projects/.../memory/`)이 있는 경우에도 워크노트는 그대로 유지한다. 두 시스템의 역할은 다르다:

| | 워크노트(프로젝트 본문) | `<프로젝트>/knowledge/` (날리지) | 에이전트 메모리 |
|---|---|---|---|
| **역할** | 작업 결과물 본체 | 프로젝트별 지식·포인터 인덱스 | 메타정보 · 포인터 · 행동 규칙 |
| **내용** | 표, 계산, 분석, 결정 사항, 출처 등 본문 | "어디에 무엇이 있다 / 무엇이 진행 중" (사람용 영구 인덱스) | "워크노트 어디에 무엇이 있다", "이 사용자는 X를 선호한다" |
| **분량** | 길어도 OK | 짧게 (포인터/요약) | 짧을수록 좋음 (인덱스 성격) |
| **편집 주체** | 사용자가 직접 검토·수정 | 사용자가 직접 관리 (에이전트는 요청 시 갱신) | 에이전트가 자동 갱신 (사용자 거의 안 봄) |
| **동기화/수명** | 영구 · 워크노트와 함께 동기화 | 영구 · 워크노트와 함께 동기화(Syncthing) | 머신-로컬 · 자주 휘발 가능 |

→ **본문은 워크노트, cross-project 인덱스는 `knowledge/`(사람용·영구), 휘발성 행동규칙·자동 포인터는 에이전트 메모리.** 같은 내용을 중복 저장하지 말 것.
> `knowledge` 와 에이전트 메모리는 둘 다 "인덱스" 성격이지만, **knowledge 는 사용자가 직접 관리하는 영구 KB(워크노트와 동기화)** 이고 **에이전트 메모리는 자동 갱신·머신-로컬**이라는 점이 다르다. 명칭 혼동을 피하려 `memory` 대신 `knowledge` 로 명명.
